# Rebase 0.1.171 Captcha and Refund Compatibility Design

## Goal

Rebase `custom_main` onto the current upstream-compatible `main`, preserve the custom payment and deployment behavior, and bring the new React frontend in line with the captcha contracts introduced in 0.1.171.

## Rebase Strategy

Use `origin/main` as the new base and replay the custom commits in their existing order. Resolve shared backend files with upstream 0.1.171 as the behavioral baseline. Reapply custom behavior only where it extends that baseline.

The remote `custom_main` history has already been published, so the final update must use `--force-with-lease` against the previously observed remote commit. The push must not proceed if the remote branch changes during implementation.

## Captcha Compatibility

The new frontend will expose one provider-neutral captcha boundary with three implementations:

- Cloudflare Turnstile uses the existing embedded widget and sends its token as `turnstile_token`.
- Tencent Captcha opens an action challenge and sends `tencent_captcha_ticket` plus `tencent_captcha_randstr`.
- Aliyun Captcha 2.0 opens an action challenge and sends `captchaVerifyParam` through the existing `turnstile_token` field, matching the backend contract.

Public settings determine the provider. More than one enabled provider is a configuration error and must not silently bypass verification. Captcha proofs remain one-time values: every submitted or potentially submitted proof is cleared after the request, and duplicate submissions stay locked.

Password login, password registration, email verification-code sending, pending OAuth verification-code sending, and pending OAuth account creation use the selected provider. Tencent and Aliyun also protect Google and GitHub OAuth start requests through the new POST start contract; Turnstile keeps its established post-callback registration coverage.

## Refund Compatibility

The 0.1.171 refund invariants take precedence during conflict resolution:

- insufficient user balance requires an explicit `force` confirmation;
- forced refunds atomically deduct only currently available non-negative balance;
- pending-refund finalization claims and completes the order transactionally;
- Stripe refund requests use stable amount-specific idempotency keys;
- the old frontend keeps the refund dialog open and exposes the force confirmation returned by the backend.

Custom behavior is layered on top:

- provider-instance snapshots remain authoritative for refund routing;
- Creem outbound refunds remain blocked and are completed through Creem webhook reconciliation;
- custom balance-credit ratios and currency-aware gateway amounts remain intact;
- subscription and global-plan entitlement deductions remain supported;
- custom audit and rollback behavior remains idempotent.

## Error Handling

Captcha SDK load failures, user cancellation, expired proofs, and provider configuration conflicts leave protected actions unavailable and show an actionable authentication error. Failed settings loading keeps the existing compatibility fallback, while backend enforcement remains authoritative.

Refund conflicts must fail closed. Missing provider snapshots, unsupported Creem outbound refunds, insufficient balance without force, and concurrent order state changes must never degrade into an unguarded gateway refund.

## Verification

Verification is layered to identify regressions precisely:

1. New frontend unit tests cover public settings, provider selection, proof mapping, OAuth start, cancellation, reset, and one-time proof consumption.
2. Backend focused tests cover captcha request contracts and refund force, atomic deduction, pending finalization, Stripe idempotency, Creem restrictions, and custom subscription/global-plan behavior.
3. Old frontend focused tests cover the 0.1.171 captcha flows and refund force dialog.
4. Full backend tests, both frontend test suites, lint/typecheck, and production builds run on the rebased `custom_main` before push.
